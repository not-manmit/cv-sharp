# Understanding the Job Ranking Engine — A Guru's Explanation

> *Come, disciple. You see a web page where you paste a resume and jobs appear
> ranked. Looks simple, yes? Behind that one click sits an entire information
> retrieval system, hand-built, algorithm by algorithm. Today I will show you
> every gear in the clock. Read slowly. Nothing here is magic.*

---

## 1. The big picture first

Think of the whole project as **a very fast, very picky librarian**.

- You hand the librarian your resume ("Here is what I know").
- The librarian has **2,000 job cards** filed in the back room.
- In about **4 milliseconds**, she returns the 10 cards that fit you best,
  and tells you *why* each one fits.

That librarian is `server.exe`. The back room is `backend/`. The front desk
where you hand over the resume is the React app in `frontend/`.

The project exists because this is an **Analysis of Algorithms** course. The
rule we set: **every algorithm written by hand, in C++, no IR/ML libraries.**
No scikit-learn, no Elasticsearch. If we used a library, we would be *users*
of algorithms — this course wants us to be *authors* of them.

```
Browser (React UI)
   │  POST /api/rank  { resume_text, top_k }
   ▼
C++ HTTP server (main.cpp)          ← listens on :8080
   │
   ▼
Ranking pipeline (pipeline.h)       ← the librarian's brain
   ├── tokenize  →  stem  →  TF-IDF        (understand the resume)
   ├── inverted index                       (find possible matches fast)
   ├── cosine + skill match → combined      (score each match)
   └── min-heap top-K + title diversity     (pick the best 10)
   │
   ▼  JSON { results: [...], timings: {...} }
Browser draws the cards, rings, and charts
```

## 2. Once at startup: building the "back room"

When `server.exe` starts, **before it answers a single request**, it does the
heavy work once and keeps it in memory forever (until you stop it). This is
the single most important performance decision in the whole system.

**Step A — Load the data** (`backend/data/jobs.json`)

2,000 synthetic job postings, each with title, company, location,
description and a list of skills. Generated by `tools/generate_jobs.py` with
**seed 42**, so the file is identical on every machine, every run. Why care?
Because benchmarks only mean something if everyone measures the same data.

**Step B — Understand every job** (`pipeline.h → build()`)

Each job description goes through the same transformation your resume will go
through later (sections 3.1–3.3 below): tokenise → stem → TF-IDF vector.
After this, every job is not *text* anymore — it is a **point in space**, a
vector of numbers.

**Step C — Build the inverted index** (`algorithms/inverted_index.h`)

A map from every *word* to the *list of jobs containing it*:

```
"dock"   → [job 41, 118, 902, 1330, ...]
"kubern" → [job 7, 240, 881, ...]
```

Why do this? Imagine searching 2,000 descriptions one-by-one for a word —
that is the *brute force* way, O(N) per query. With the index, you go
straight to the shelf where that word lives and touch **only those jobs**.
Disciple, this one structure is what gave us a **13.9× speedup** in our
benchmarks. It is how real search engines work, scaled down to a classroom.

## 3. Now a resume arrives — the 6-stage journey

Every stage records how many milliseconds it took (`timings` in the JSON),
so you can *see* where the time goes. The UI shows this in the stats row.

### 3.1 Tokenise — turn text into words
*File: `backend/algorithms/tokenizer.h`*

- Lowercase everything ("Docker" = "docker").
- Split on non-letters.
- Throw away **stop words** — "the", "and", "with", "experience"... words
  that appear in *every* document and carry zero signal. The list lives in
  `backend/data/stopwords.txt`. Why remove them? Because if a word appears
  in all 2,000 jobs, it cannot help you *distinguish* between them.
- **The exception (our own rule):** tiny 2-letter tech tokens like `ai`,
  `ml`, `go`, `ui` would normally die as stop words, but they're real
  skills. So the tokenizer keeps a small whitelist. *"The rule exists to
  remove noise — but a rule that deletes 'AI' from an AI resume is a foolish
  rule,"* and so we patched it.

### 3.2 Stem — crush words to their root
*File: `backend/algorithms/stemmer.h` — full 5-step Porter Stemmer*

"connecting", "connected", "connection" → all become `connect`.

Why? Without this, a resume saying "connecting services" and a job saying
"connection pooling" would look like *different* words and never match.
Stemming is crude but effective — it multiplies your matching power without
storing anything extra. The stemmer is ~200 lines of pure suffix rules; we
implemented all 5 steps ourselves because the course demands it.

### 3.3 TF-IDF — give every word a weight
*File: `backend/algorithms/tfidf.h`*

Two ideas glued together:

- **TF** (term frequency): a word you repeat a lot matters more *to you*.
- **IDF** (inverse document frequency): a word that's rare across the corpus
  is more informative. "the" → IDF ≈ 0. "kubernetes" → IDF high.

Each document becomes a sparse vector `(word → weight)`, and we store its
**L2 norm** (its length) so similarity becomes one division later.
This is the "understanding" step: text has become geometry.

### 3.4 Candidate filter — the inverted index query
*File: `algorithms/inverted_index.h`*

We don't score all 2,000 jobs. We ask: *which jobs share words with this
resume?*

- Collect the resume's unique terms.
- Sort them by **rarity** (rarest first) and look up only the **20 rarest**
  in the index.
- A job is a candidate if it overlaps enough of them (threshold adapts to
  the query length).

Why only 20 rarest? Two engineering truths we hit and documented:

1. Common words ("work", "team") point to thousands of jobs — following
   them is wasted work. The rare words are the *fingerprint* of the query.
2. A long resume shares *some* word with nearly every job, so a strict
   "must match ALL words" rule would return everything and help nothing.

This stage is where the O(N) → O(Σ df(t)) win happens. In the response you
will see `candidates` (say, 400) versus `total_jobs` (2,000).

### 3.5 Scoring — cosine similarity + skill match
*File: `algorithms/cosine.h` + scoring block in `pipeline.h`*

For each candidate only, two signals:

**Cosine similarity** — the *angle* between the resume vector and the job
vector. 1.0 = same direction = perfect overlap; 0 = nothing in common.
Why angle and not distance? Because a 500-word resume and a 50-word job
should still be able to "point the same way". Length must not be punished.

**Skill match** — the resume's words are checked against the job's
structured skill list with **word-boundary awareness**: looking for
"java" never matches "javascript", "go" never matches "google". Then:

```
skill_match = (job skills found in resume) / (all job skills)
```

Why add this second signal at all? Because cosine alone had a blind spot —
a resume full of beautiful prose about "working with databases at scale"
scores well on cosine but may not literally say **PostgreSQL**. The skill
component grounds the match in hard facts.

**The blend (SPEC §3.10):**

```
combined = 0.7 × cosine + 0.3 × skill_match
```

70% "reads similar", 30% "has the exact skills". The weights live in
`kAlphaCosine` / `kBetaSkill` in `pipeline.h` — one line to retune the
whole philosophy.

### 3.6 Top-K with a min-heap + title diversity
*File: `algorithms/heap_topk.h` + tail of `pipeline.h::rank()`*

You asked for the top 10. Two ways to do it:

- **Sort all scores, take first 10** → O(N log N). Wasteful: you sorted
  400 numbers to keep 10.
- **Min-heap of size K** → O(N log K). Keep a heap holding only the best K;
  for each new score, if it beats the smallest thing in the heap, swap.
  The heap stays tiny, so every operation is nearly free.

Measured result: **8.9× faster** (0.022 ms → 0.003 ms at N=2000). Tiny in
absolute terms, but that's the point of the assignment — *prove* the
complexity difference with numbers.

**Then the real-world patch:** raw scores produced ten identical-looking
"Frontend Engineer" results (equal scores tie, and duplicates win ties). So
we take a *widened* pool (4×K + 20) and then walk it keeping **at most one
job per unique title**, filling from leftovers only if distinct titles run
out. This is not in any textbook — it's what happens when theory meets a
templated dataset, and we fixed it honestly.

### 3.7 The response

```json
{
  "results": [ { "rank": 1, "title": "...", "cosine_score": 0.42,
                 "skill_match_score": 1.0, "combined_score": 0.60,
                 "matched_terms": ["kubernetes","docker"] } ],
  "timings": { "tokenize_ms": 0.2, "total_ms": 4.08 },
  "total_jobs": 2000, "candidates": 412
}
```

`matched_terms` answers the disciple's eternal question: *"but WHY did it
match?"* — the UI shows them as chips on each card.

## 4. The two experiments (the actual course deliverable)

*File: `backend/benchmark.h`, CLI `experiments/run_benchmarks.cpp`*

| # | Baseline (naive) | Optimised | Measured speedup | Target |
|---|---|---|---|---|
| 1 | scan all N jobs | inverted index | **13.9×** | ≥ 3× |
| 2 | full sort O(N log N) | min-heap top-K O(N log K) | **8.9×** | ≥ 1.5× |

Methodology matters as much as the code:

- **Warm-up runs first** (10×) — the first call is always slow (cold CPU
  cache, branch predictor warming up). Discard it.
- **Median of 30–100 runs**, never a single measurement — one OS hiccup
  would lie to you. Median laughs at outliers.
- Each data point for experiment 2 uses **real scores with a random seed**,
  so the "random" input is the *same* random input for both algorithms —
  a fair race.

Why does this matter? Because a benchmark you rigged is not a benchmark,
it's a story. The course wants measurements.

## 5. The server — why it looks the way it does
*File: `backend/main.cpp`*

- **cpp-httplib (`third_party/httplib.h`)** — a single-header HTTP library.
  No package manager, no DLLs, no `npm install` for C++. We vendored it
  (copied it into the repo) so the project builds on any machine offline.
  Same for `nlohmann/json.hpp` — JSON in/out without writing a parser
  (that would be reinventing the wrong wheel; our course algorithms are in
  `algorithms/`, not in HTTP plumbing).
- **Four endpoints**, because V1 needed exactly four: rank, jobs list,
  benchmark, health. Extra endpoints = extra surface = extra bugs.
- **Static mount** — `set_mount_point("/", "frontend/dist")` means the same
  process serves both the API *and* the compiled React app. One exe, one
  port, one thing to start. No Nginx, no Docker, nothing to explain wrong
  in a demo.
- **CORS headers** are set so the Vite dev server (port 3000) can talk to
  the backend (port 8080) during development.
- **Validation** — empty resume, top_k out of range, unknown route → all
  answered with proper HTTP 400/404 + a JSON error body. A server that
  crashes on bad input is a demo, not a system.

## 6. The frontend — small on purpose
*Files: `frontend/src/App.jsx` + `components/`*

| Component | Its one job |
|---|---|
| `App.jsx` | Two tabs (Rank / Benchmarks), health status, layout |
| `ResumeUpload.jsx` | Textarea, Top-K select, validation (≥50 chars), submit |
| `RankedList.jsx` | Draw ranked cards: score ring, cosine/skill bars, chips |
| `BenchmarkDashboard.jsx` | Run experiments, KPI speedups, table, CSV download |
| `TimingChart.jsx` | Chart.js wrapper — line/bar, log-scale toggle |
| `api/client.js` | All `fetch` calls in one place |

Why so few files? Because the *interesting* code is in C++ — the UI exists
to make the backend's answers visible. State is simple: `useState` only, no
router, no Redux. The PRD's job was "a clean window into the engine", not
"an enterprise SPA".

**Dev vs prod:** in dev, Vite serves the UI on :3000 and *proxies* `/api` to
:8080 (see `vite.config.js`) — so the code never cares which port it's on.
In prod, `npm run build` freezes the UI into static files that the C++
server serves itself.

## 8. Honest deviations (and why)

A guru must also admit where the book and the road differ:

1. **Index queries use the 20 rarest terms, not "ALL terms must match".**
   Strict AND on a long resume degenerates — it matches almost nothing;
   loose OR matches everything. Adaptive overlap on rare terms is the
   engineering middle ground. Documented in `inverted_index.h`.
2. **Title diversity pass** after the heap. Textbook top-K has no notion of
   "the user is bored seeing the same title 10 times". Real products do.
3. **Stop-word whitelist** for 2-letter tech tokens (ai, ml, go...).
4. **Cut for V1** (all "Should" items in the PRD, not "Must"): PDF parsing,
   BM25, KMP phrase search, fuzzy Levenshtein matching, unit test suites,
   ground-truth quality evaluation. *A focused V1 that beats its targets
   beats a bloated V1 that misses them.* These are V2 work.
